# Threshold cryptography

Distribute a private key across `n` parties such that any `t` can jointly
sign/decrypt, but no single party (or any `t-1` colluding) can.

## Files

- `distributed_key_generation.py` — Pedersen DKG: parties jointly generate a
  key with no single party (not even a dealer) ever knowing the whole secret
- `threshold_schnorr_signature.py` — t-of-n Schnorr signing from
  secret-shared key material (the idea behind FROST)

Both use a toy subgroup of order `q = 11` inside `p = 23`, generated by
`g = 4` (check: `4^11 mod 23 = 1`, and no smaller power of 4 equals 1 — so 4
has order 11 in this group). This lets every Lagrange coefficient below be
computed by hand mod a small prime.

---

## 1. Pedersen distributed key generation — step by step

**The idea in one sentence:** instead of one dealer choosing the secret key
(a single point of failure — what if the dealer is malicious, or gets
hacked right after generation?), have *every* party contribute a random
piece, and let the group secret be the sum of everyone's contributions —
nobody ever computes that sum in the clear.

### Steps

1. **Every party `i` runs its own Shamir sharing.** Party `i` privately
   picks a random local secret `z_i` and a random polynomial
   `f_i(x) = z_i + b_i·x mod q` (degree matches the desired threshold minus
   one), just like in `02_secret_sharing/shamir_secret_sharing.py`.
2. **Every party publishes Feldman-style commitments** to its own
   polynomial's coefficients: `C_i,0 = g^(z_i)`, `C_i,1 = g^(b_i)`, etc.
3. **Every party sends every other party a private share** of its own
   polynomial: party `i` sends party `j` the value `f_i(j)`.
4. **Every party verifies every share it receives** against the sender's
   public commitments — exactly the Feldman check from `02_secret_sharing/`.
   Any inconsistency publicly identifies a cheating contributor.
5. **Each party sums the shares it received from everyone** (including
   itself) to get its own **final share** of the *group* secret:
   `final_share_j = Σ_i f_i(j)`.
6. **The group public key is computable by anyone**, from public data only:
   `Y = Π_i C_i,0 = Π_i g^(z_i) = g^(Σ_i z_i)` — the product of everyone's
   commitment to their own local secret equals `g` raised to the *sum* of
   all local secrets, which is exactly the group's private key exponent.

### Why no one ever knows the full secret

The group secret is `x = Σ_i z_i mod q` — a sum of numbers, each of which
only its own contributor ever saw. Nobody ever computes this sum directly;
they only ever hold `final_share_j`, one point on the *implied* combined
polynomial `F(x) = Σ_i f_i(x)` (which nobody explicitly constructs either —
it exists only implicitly, as the sum of everyone's individual, never-fully-
combined contributions).

### Worked example (toy: n=2, t=2, order-11 subgroup, g=4, p=23)

Party 1 picks local secret `z1 = 3`, coefficient `b1 = 2`:
`f1(x) = 3 + 2x mod 11`.
Party 2 picks local secret `z2 = 5`, coefficient `b2 = 6`:
`f2(x) = 5 + 6x mod 11`.

1. Cross-shares: `f1(1)=5, f1(2)=7`; `f2(1)=0, f2(2)=6`.
2. Party 1's final share: `f1(1) + f2(1) = 5 + 0 = 5`.
   Party 2's final share: `f1(2) + f2(2) = 7 + 6 = 13 mod 11 = 2`.
3. Group secret (never assembled by anyone) would be `z1+z2 = 8`.
4. Group public key from commitments only:
   `C1,0 = 4^3 mod 23 = 18`, `C2,0 = 4^5 mod 23 = 12`,
   `Y = 18·12 mod 23 = 216 mod 23 = 9`.
5. **Sanity check** (only possible here because we're peeking, for
   demonstration — nobody would do this in real life): reconstruct the
   secret via Lagrange from the two final shares `(1,5)` and `(2,2)`:
   `λ1=2, λ2=10` → `2·5 + 10·2 = 30 mod 11 = 8` — matches `z1+z2=8`, and
   `g^8 mod 23 = 9` matches the publicly-derived `Y=9`. ✓

Run `distributed_key_generation.py` for the 3-party version over the real
1536-bit group, with every Feldman check actually performed in code.

## 2. Threshold Schnorr signing — step by step

**The idea in one sentence:** run the ordinary Schnorr signing equation
"in parallel" across `t` parties, each contributing a term built from their
own key share and a Lagrange weight that makes the pieces add up correctly
— and the final signature is verified exactly like a normal single-signer
Schnorr signature.

### Setup

`t` of `n` parties hold Shamir shares of a group private key `x`
(from Shamir sharing or DKG above), with public key `Y = g^x`.

### Steps, for a chosen set of `t` signers

1. **Each signer picks a random nonce** `r_i` and publishes a commitment
   `R_i = g^(r_i)`.
2. **Aggregate the nonce commitments:** `R = Π_i R_i mod p`.
3. **Compute the Fiat-Shamir challenge** the same way ordinary Schnorr
   does: `c = H(R, Y, message)`.
4. **Each signer computes a partial signature**, weighting its own share by
   its **Lagrange coefficient for this specific set of signers**:
   `partial_i = r_i + c · λ_i · share_i mod q`,
   where `λ_i` is exactly the Lagrange basis coefficient from secret
   sharing — the same tool that reconstructs a secret from shares is reused
   here to reconstruct a *signature* from partial signatures, without ever
   reconstructing the secret itself.
5. **Combine:** `s = Σ_i partial_i mod q`.
6. **Verify exactly like single-signer Schnorr:** `g^s == R · Y^c mod p`.

### Why the combination equation checks out

Expand `s = Σ_i (r_i + c·λ_i·share_i) = Σ_i r_i + c · Σ_i (λ_i·share_i)`.
The first sum is just the combined randomness, matching `R = Π g^(r_i)`
in exponent form. The second sum, `Σ_i λ_i·share_i`, is *exactly* the
Lagrange reconstruction formula for the group secret `x` — evaluated
implicitly, inside the exponent, without anyone ever computing `x` in the
clear. So `s = r_total + c·x`, which is precisely the single-signer Schnorr
response equation, just computed collaboratively.

### Worked example (continuing the toy group: p=23, g=4, q=11)

Group secret `x=7`, coefficient `a1=5`: shares `f(1)=1, f(2)=6, f(3)=0`.
Public key `Y = g^7 mod 23 = 8`.

Signers = parties `{1, 2}` (any 2 of the 3 would work).

1. Nonces: `r1=3 → R1=4^3 mod23=18`; `r2=4 → R2=4^4 mod23=3`.
   `R = 18·3 mod23 = 54 mod23 = 8`.
2. Challenge (toy, fixed for illustration): `c = 5`.
3. Lagrange coefficients for signer set `{1,2}`: `λ1=2, λ2=10` (identical
   computation to the DKG example above — same formula, same signer
   positions).
4. Partial signatures:
   `partial_1 = r1 + c·λ1·share_1 = 3 + 5·2·1 = 13 mod 11 = 2`
   `partial_2 = r2 + c·λ2·share_2 = 4 + 5·10·6 = 4 + 300 = 304 mod 11 = 7`
5. Combined: `s = 2 + 7 = 9`.
6. Verify: `g^s = 4^9 mod 23 = 13`. `Y^c = 8^5 mod 23 = 16`.
   `R·Y^c = 8·16 mod 23 = 128 mod 23 = 13`.
   `13 == 13` ✓ — a completely standard Schnorr verifier, with no idea a
   threshold protocol was involved, accepts.

Run `threshold_schnorr_signature.py` for a 2-of-3 signature over the real
1536-bit group.

## When to use

- Custody of a high-value key (exchange hot wallet, root CA key, blockchain
  validator key) where no single machine or operator should ever hold the
  full secret.
- You want signatures indistinguishable on-chain from a normal single-key
  signature (unlike naive n-of-n multisig, which is visibly a multisig
  script) — see `06_multisig_aggregate_signatures/`.

## When *not* to use

- A single HSM-protected key with good operational controls already meets
  your threat model — threshold crypto adds real coordination complexity
  (multiple communication rounds, liveness requirements on `t` parties).
- Your parties can't reliably stay online/reachable — most threshold signing
  protocols need `t` parties simultaneously online for each signature.
- You need auditability of *who* signed — plain threshold signatures hide
  which specific `t` of `n` parties participated (that can be a feature or
  a bug depending on your use case).

## Caveats in this code

- Semi-honest security only — no misbehavior detection during signing
  (production systems like FROST add commitments per round and abort paths
  for provably malicious participants).
- No robustness: if any of the chosen `t` signers drops out mid-protocol,
  this demo does not retry with a different subset.
- Real threshold-ECDSA (as opposed to threshold-Schnorr shown here) is
  substantially harder — ECDSA's non-linear structure needs extra
  machinery (e.g. Paillier-based multiplicative-to-additive share
  conversion in GG18/GG20/CGGMP21). This demo sticks to Schnorr, where
  linearity makes threshold signing straightforward.

## Real-world examples

- **Distributed key generation**: randomness beacons like `drand` (the
  League of Entropy) use DKG so that no single node can predict or bias the
  publicly-verifiable random output. Distributed Validator Technology (DVT)
  projects in the Ethereum ecosystem (e.g. Obol, SSV Network) use DKG to
  split a validator's signing key across multiple independent node
  operators, so no single operator's failure or compromise can slash the
  validator or take it offline.
- **Threshold Schnorr (FROST)**: actively being integrated into Bitcoin
  wallet software for collaborative custody now that Taproot makes Schnorr
  the native signature scheme — wallets exploring FROST-based multi-device
  signing avoid ever assembling the full private key on any single device,
  including the user's own phone or hardware wallet, while producing a
  signature that looks like an ordinary single-key spend on-chain.

## Decision guide: which one do I need?

- **Are you setting up a NEW key from scratch, and want to guarantee no
  single party (not even a "dealer") ever sees the full private key, even
  during generation?**
  → Distributed key generation (Pedersen DKG).
- **Do you already have a key split via secret sharing (or DKG), and need
  a subset of parties to actually USE it — sign a message or decrypt
  something — repeatedly, over time?**
  → Threshold Schnorr signing (or the equivalent threshold decryption
  procedure for an encryption scheme, not included as a standalone demo
  here but following the same pattern).
- **Do you specifically need ECDSA-compatible signatures (e.g. for older
  Bitcoin/Ethereum wallets that don't yet support Schnorr), not Schnorr?**
  → Neither script here directly — you need threshold ECDSA (GG18, GG20, or
  CGGMP21), which needs extra machinery (see the caveats section) beyond
  what's demonstrated in this repo.
